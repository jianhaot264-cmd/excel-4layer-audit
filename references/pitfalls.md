按"踩到的概率 × 破坏力"排序。动手前先扫一遍。

## P1. editor_sdk 写出的公式，等号在 `<f>` 标签内部

**现象**

经 `tencent-local-office-edit`（`edsdk.py`）保存的表格，`xl/worksheets/sheetN.xml` 里是：

```xml
<f>=作答区!A20</f>                          <!-- 普通公式 -->
<f t="array" ref="B20">=INDEX(...)</f>      <!-- 数组公式：标签带属性 -->
```

OOXML 规范要求 `<f>` 的内容**不含前导 `=`**。

**后果**

- Excel/WPS 多数版本能容错打开，所以肉眼看不出来。
- 但 `openpyxl` 读出来是 `"==作答区!A20"`；只要有一次"读出→写回"的脚本往返，公式就真正损坏。
- 属于"看起来交付成功、实际埋雷"的典型。

**修法**

用 `scripts/fix_formula_tags.py`（直接改 zip 内 XML，图表/样式/共享字符串全不动）：

```bash
python scripts/fix_formula_tags.py 成品.xlsx
```

**⚠️ 最容易被漏掉的点**：只搜字面量 `<f>=` 是不够的——数组公式的标签带属性（`<f t="array" ref="B20">=`），`str.replace("<f>=", "<f>")` 完全匹配不到。正确做法是抓 `<f(\s[^>]*)?>(.*?)</f>` 再判断 group(2) 是否以 `=` 开头。

**校验口诀**：永远抓完整标签再判断内容首字符，不要匹配字面量前缀。

## P2. 改 xlsx 磁盘文件前，必须先释放 editor_sdk 的文件锁

**现象**

只要表格引擎里还有该文件的实例（**包括宿主预览面板自动注册的那个实例**），磁盘文件就是 deny-write：

- `os.replace(tmp, src)` → `PermissionError [WinError 183] / [WinError 32]`
- `open(src, "r+b")` → `PermissionError [Errno 13]`

**正确顺序**

```bash
# 1. 找出所有实例（可能同时有路径型 id 和宿主预览的 UUID）
python edsdk.py call get_pool_status
# 2. 逐个关闭
python edsdk.py call close_file file_id=<id> force=true
# 3. 删掉同目录残留的归属文件
rm -f "~/路径/~\$文件名.xlsx"
# 4. 带重试地落盘（每次间隔 3 秒）
```

**代价提醒**：`shutdown` 是最后手段——服务停掉后 **CLI 无法再连上，也不会自动恢复**，只能等宿主按需重启（代价：会话内后续的 `sheet_*` 操作全部不可用，且用户的应用内预览可能一片空白）。**能只 `close_file` 就别 `shutdown`。**

另一个副作用：宿主预览实例被关闭后，用户面前的预览面板会失效。落盘完成后应重新用 `present_files` 呈现一次。

## P3. 新版独占函数导致 `#NAME?` 并连锁毁掉答案区

**高风险函数**：`UNIQUE` `FILTER` `SORT` `SORTBY` `SEQUENCE` `XLOOKUP` `LET` `TEXTJOIN` `IFS` `MAXIFS` `MINIFS` `RANDARRAY` `TAKE` `DROP`。

**为什么破坏力大**：一旦用 `UNIQUE` 生成"品牌清单"这类基础数据，下游所有 `INDEX`/`MATCH`/`SUMIFS` 都引用它——一个 `#NAME?` 会让整张答案表连带报错，而不只是一个小格子。

**规则**：清单类内容**写静态文字**。清单本身没有计算价值，稳定性远比"自动扩展"重要。

**去重计数的经典替代**：

```
单条件去重计数  =SUMPRODUCT(1/COUNTIF(范围,范围))
分组去重计数    =SUMPRODUCT((组=条件)/COUNTIFS(组,组,键,键))
第 k 名提取     =INDEX(名称区,MATCH(LARGE(值区,k),值区,0))  +  =LARGE(值区,k)
排名            =RANK(值,值区)
```

## P4. `max_row` 虚高，公式引用范围写错

表格的 `max_row` 常因残留格式而远大于真实数据行数（实测：数据到 78 行，`max_row` 却是 84）。

**后果**：公式引用 `$2:$84` 时把空行也纳入，`SUMPRODUCT` 里空单元格按 0 参与运算通常无害，但 `COUNTIF`/`AVERAGE` 类的分母会被污染，去重计数也会算错。

**做法**：先用 `sheet_get_used_range` 或逐行扫非空，确认**真实**数据边界，公式严格按真实边界写。审计时会核对"引用区间"与"真实有值行"是否一致。

---

## P5. 重复记录：默认全量统计，把去重结果写成备注

出题人常在数据源**表尾追加几条与前面完全重复的记录**，且打乱日期排序来制造"脏数据痕迹"。

**处理原则**

1. **默认按原表全量统计**——数据源就是事实，未经说明不应擅自去重。
2. 但在交付物里**显式记录**：哪几行重复、与哪几行重复、去重后结论会怎么变。
3. 这样无论接收方按哪种口径判卷，都不会被扣分。

**务必同时检查**：某个"重复值"是否其实是**合法的两笔业务**（如同一商品在不同日期、不同城市各卖一次）。只有七个字段全同才算重复。

## P6. 图表与明细表口径不一致

明细表列出全部 N 个类别（含 0），图表只画非零的 M 个——这是**合理的**（0 值画进图里只是噪声），但必须**加一行注释说明**，否则会被当成疏漏。

图表数据源要单独放在一块整齐的降序区域（如 `作答区!$A$52:$B$61`），图表直接引用它，不要引用零散的明细单元格。

---

## P7. 浮点与显示值的"假不一致"

- `round()` 是**银行家舍入**：`round(448.155, 2)` → `448.15`，而 Excel 单元格格式 `#,##0.00` 显示为 `448.16`。两者都没错，别为了对齐去改数据。
- 比对时用容差 `abs(a - b) < 0.005`，不要用 `==`。
- 排名并列时（如两个 0 值并列第 9），`RANK` 会给出相同名次，这是正确行为。

---

## P8. 比对脚本按下标对位置 → 整片假报错

明细表通常是**原始顺序**（按首次出现），而排名/答案表是**降序**。用同一个 `i` 去索引两张表，会得到"10 项全不一致"的假警报。

**做法**：一律**按名称（品牌/商品名）查字典**再比对，不要 `exp[i]` 对齐 `明细[i]`。

## P9. 委派表格子代理时不要"先读一半再委派"

表格任务一旦确定要走 `tencent-docs-sheetagent`，就应把**整个**任务一次性交给它，不要自己先读数据、先做格式、先改一部分再委派剩下的——会把任务割裂，且子代理拿到的不是全局观。交给它的前置工作只有一项：解析出 `file_id`。

## P10. 分类列里混入异质取值 → 按该列筛选会静默漏行

**实例（真实踩到）**：数据源的「零售商」列本应是门店名（沃尔玛 / 全家 / 喜市多 …），但有 11 行填的是门店**代码** `711`（7-Eleven）——数字，不是文本。

**为什么危险**

- 这类错误**不会报错**，只会让统计结果悄悄少算。
- 本例中它是无害的（两个问题分别按"品牌"和"零售商='全家'"统计，`711 ≠ 全家`），但如果题目问的是"各零售商的销量"，这 11 行就会被整体漏掉。
- 同时它也污染了该列的"取值分布"，容易让人误判该列只有几个分类。

**发现方式**：对**纯表格工作表**逐列统计"数值 vs 文本"的类型构成，出现两类都 ≥2 的列就报出来。

**处理原则**

1. 先判断是否影响结论：
   - 若该列只是被"等于某个文本值"筛选 → 异质值天然被排除，**不影响**，在交付说明里点一句即可。
   - 若该列被用于分组、汇总、去重计数或范围筛选 → **必须先与用户确认口径**，不能默默算。
2. 无论如何都要在交付说明的"发现的数据问题"里记一笔——这正是评审方会问的点。

配套检查：如果某分类列出现了**同义异形**的取值（`7-11` / `711` / `7-Eleven` 混用），需要人工归并后再统计。

## P11. 把"读到的缓存值"当成"真值"（最隐蔽的一类）

**现象**：`openpyxl.load_workbook(p, data_only=True)` 读出的公式结果，来自 xlsx 里的 `<v>` 标签——那是**上一次保存这个文件的程序**算出来的。用它去比对期望值，只证明了"写入程序"和"期望值"一致。

**为什么隐蔽**：这条路径上所有的检查都会全绿，包括"独立重算"——因为独立重算比的是**同一份缓存**。用户双击打开看到的可能完全是另一组数字。

**修法**：必须有一个**不读缓存**的引擎强制重算。见 `scripts/recalc_verify.py`：

```
① 缓存值 vs 重算值  → 找陈旧/错误缓存
② 重算值 vs 期望值  → 权威结论
③ 重算后错误值扫描  → 重算才暴露的 #REF!/#VALUE!
```

**判据**：L2 报 0 处不一致，才允许说"用户在 Excel 里看到的会是这个数"。

## P12. 直接往 XML 里加单元格时，忘了包 `<row>`

**现象**：往一个尚不存在的行写单元格，只把它插到最后一个 `<row>` 之后：

```xml
...</row><c r="A80" t="s"><v>83</v></c></sheetData>   <!-- 非法！ -->
```

`<c>` 成了 `<sheetData>` 的直接子节点。Excel 打开时该单元格**静默丢失**（openpyxl 读回是 `None`），不报错。

**修法**：新建行必须整行包装，并插到"最后一个 `r` 小于目标行的 `<row>`"之后：

```python
new_row = '<row r="%d" spans="1:%d">%s</row>' % (row, col_idx + 1, cell_xml)
```

**通用纪律**：任何"直接改 XML"的操作，写完必须
1. 用 `ElementTree` 解析每个 xml 部件；
2. 搜 `< /row>\s*<c ` 这种"脱离行的单元格"结构；
3. 用 openpyxl 读回目标单元格确认值真的落进去了。
`scripts/patch_cells.py` 已把这三步内建为"复验失败自动回滚"。

**另一个同类坑**：公式单元格必须有 `<v>` 缓存值，否则部分阅读器显示空白。`audit_xlsx.py` 已加检查项。

## P13. 判定"用的是哪个办公引擎"时的三个坑（会导致"验了个寂寞"）

**坑 1：WPS 通过 COM 自报名返回 `Name = "Microsoft Excel"`**

```python
app = win32.DispatchEx("KET.Application")
app.Name     # -> 'Microsoft Excel'   ← 假的！
app.Version  # -> '12.0'              ← 真的（Excel 是 16.0）
app.Path     # -> 'E:\\WPS Office\\12.1.0.28043\\office6'   ← 真相在这
```

WPS 为了兼容 VBA / COM 客户端会谎报名字。**只看 `Name` 会得出"我在用 Excel 验"的错误结论**，实际上跑的是 WPS——这样"双引擎交叉验证"就退化成了同一个引擎跑两遍。

**正确判定**：`ProgID` + 安装路径 + 版本号三者共同确认。

**坑 2：`Excel.Application` 这个 ProgID 可能被 WPS 接管**

WPS 安装时可选择"关联 Office 格式"，接管后 `DispatchEx("Excel.Application")` 拉起来的其实是 WPS。所以必须校验 `app.Path` 是否真的指向 Microsoft Office 目录，不符就警告。

**坑 3：WPS 常装在非 C 盘 → 路径探测会误判"没装"**

实测 WPS 装在 `E:\WPS Office\12.1.0.28043\office6`。之前用
`Test-Path "C:\Program Files\WPS Office"` 判空就下了"未安装"的结论，**是错的**。

**正确探测顺序**：
1. `DispatchEx(ProgID)` —— **最可靠**，注册了就能起来
2. 读注册表 `HKLM\SOFTWARE\Kingsoft` / `HKLM\SOFTWARE\WOW6432Node\Kingsoft`
3. 全盘找可执行文件（含非系统盘）
4. 常见路径 `Test-Path` —— **只能作为最后的辅助，不能作为"没装"的依据**

**教训泛化**：判断"某软件在不在"，**不要用文件路径探测做否定判断**，要用能力探测（能不能起来）。

> 补充实测：**`KWPS.Application`（WPS 文字）也把 `Name` 自报成 `"Microsoft Word"`**，
> 版本 12.0、路径 `E:\WPS Office\...`。所以这套判定规则在表格侧和文档侧**完全通用**。

## P14. 用 COM 打开工作簿做验证后，要确认文件没被改

COM 引擎打开文件时如果没设 `ReadOnly=True`，或者退出时用了 `SaveChanges=True`，会**悄悄改掉原文件**——验证完文件却变了，此前所有哈希与结论全部失效。

**纪律**：
```python
wb = app.Workbooks.Open(path, UpdateLinks=0, ReadOnly=True,
                        IgnoreReadOnlyRecommended=True, Notify=False, AddToMru=False)
...
wb.Close(SaveChanges=False)      # 必须显式 False
app.Quit()                       # finally 里执行，防孤儿进程
del wb, app; gc.collect()
```

**验证后必做**：重新算一遍 SHA256，确认与验证开始时一致。
`recalc_verify.py` 已按此实现；用完后建议手动核对一次哈希。

## P15. Word 对象模型：`Document.Fields` 已经包含表格里的域

**现象**：想同时收集"正文的域"和"表格里的域"，于是遍历了两遍：

```python
for i in range(1, doc.Fields.Count + 1): ...              # 已包含表格内的域
for ti in range(1, doc.Tables.Count + 1):                 # 又收一遍 → 重复
    fs = doc.Tables(ti).Range.Fields
```

结果同一个 `=SUM(ABOVE)` 被报了两次，域计数虚高，读者会误以为文档里有两个公式。

**正解**：`Document.Fields` 是**全文档**的域集合，表格内的域已在其中，只遍历它即可。
`doc.Tables(i).Range.Fields.Update()` 仍值得单独调一次作为保险，但**不要**再用它来收集。

**推广**：凡是"容器 → 子容器 → 子对象"的多层对象模型（Word 的文档→表格→域、
Excel 的工作簿→工作表→图表、PPT 的文档→幻灯片→形状），都要先确认
**上层集合是否已包含下层对象**，否则很容易重复计数。

## P16. Word 的"重算"是 `Fields.Update()`，不是 `Calculate`

`=SUM(ABOVE)` 这类表格公式在 Word 里是**域（Field）**，不是 Excel 那样的公式单元格。

- 没有 `Calculate` 可调；正确做法是 `doc.Fields.Update()`，并对每个表格补一次
  `doc.Tables(i).Range.Fields.Update()`。
- 域结果同样**缓存**在文件里 → 与 Excel 的 `<v>` 属同一类盲区。
  想确认"更新真的生效了"，就把缓存**故意写错**再跑：
  `python scripts/make_docx_field_sample.py` 会生成一个 `=SUM(ABOVE)` 缓存写成 `999999`
  的样本，正确的两引擎都应算回 `60`；若都报 `999999`，说明它们只读了缓存，验证无效。
- 用 COM 读完文档后，关闭必须显式 `doc.Close(SaveChanges=0)`（即 `wdDoNotSaveChanges`），
  否则域更新后的结果会被写回文件，文件就被悄悄改动了。

## P17. 脚本直接生成的 xlsx 有两个先天特征，会让常规检查集体失灵

用 openpyxl / xlsxwriter **直接写出来**的文件（没经过真实引擎保存）：

1. **公式单元格没有 `<v>` 缓存**。`data_only=True` 读回全是 `None`。
   于是 L3 的"期望值比对"、L4 的"按值比对不变量"全部失效——不是报错，是**静默地比了个寂寞**。
2. **没有 `xl/sharedStrings.xml`**（openpyxl 用内联字符串）。
   任何假设"字符串一定在共享字符串表里"的脚本都会 `KeyError`。

**修法**

- 要做值比对，先把文件**过一遍真实引擎**：打开 → `CalculateFullRebuild()` → `Save()` → 关闭。
  （`selftest.py` 里的 `materialize()` 就是这个动作，可直接抄。）
- 改单元格的脚本要兼容"没有共享字符串表"的情况：改用合法的**内联字符串**
  `<c t="inlineStr"><is><t>…</t></is></c>`（`patch_cells.py` 已内置该回退）。

**判别方法**：`'xl/sharedStrings.xml' in zipfile.ZipFile(p).namelist()`，以及任一公式单元格
`data_only` 读回是否为 `None`。

## P18. 逐格 diff 的两个坑：视图不一致 + 遍历范围不一致

**坑 1：拿"公式视图"去比"数值视图"。**
`load_workbook(p)` 对公式单元格返回公式文本，`load_workbook(p, data_only=True)` 返回缓存值。
一个未经引擎保存的原文件（公式、无缓存）去比一个被引擎保存过的成品（有缓存值），
**每个公式单元格都会被误判成"内容被覆盖"**——而实际上一个字都没改。

**正确做法**：
- 原来是公式的单元格 → 只检查成品里它**仍然是公式**（若变成了硬编码常数，才是真的被覆盖）；
- 静态值 → 用 `data_only` 两边同视图比较，数值带容差。

**坑 2：diff 只遍历原文件的 `max_row / max_column`。**
成品里**超出原表范围**的新增单元格（例如新写的作答行）根本不会被扫到，
"新增单元格"统计永远是 0，看起来像什么都没发生。

**正确做法**：遍历两份文件行列范围的**并集**（`max(两边 max_row)` × `max(两边 max_column)`）。

`audit_xlsx.py` 的 `--orig` 分支已按此实现，并新增了"公式被硬编码常数替换"这一独立检查项。

## P19. 检查工具自己也会静默失效 —— 所以必须有自检

**真实案例**：`fix_formula_tags.py` 的正则写成了 `<f(\s+[^>]*?)>(=)`，
`\s+` 要求 `<f` 后面**必须有空格**，于是只匹配得到带属性的 `<f t="array">=…`，
**最常见的 `<f>=…` 一个都匹配不到**。而它跑完报的是"0 处需修正，文件已合规"——
一个**什么都不做的修复工具，输出看起来完全正常**。

之前没发现，是因为当时文件已经被别的手段修好了，脚本报 0 被误读成"本来就合规"。

**教训与纪律**

1. **修 bug 的工具必须用"故意造坏"的样本来验证**，不能只拿已经修好的文件跑一遍看它说 0。
   `selftest.py` 会专门生成 `plain`（`<f>=`）和 `array`（`<f t="array">=`）两种坏样本，
   并断言修复后残留为 0。
2. **写正则匹配标签时，属性段必须是"可选"**（`(\s[^>]*)?`），不要写成 `(\s+[^>]*?)`。
3. **任何"0 处需修正"的输出都要多想一步**：是真的很干净，还是工具根本没扫到？
   用一个已知是坏样本的文件反测一次，才能确定。
4. 加了守卫别忘了 `import os` 之类的基础项——本次就因为补了 `os.path.isfile` 却没补 `import os`
   被自检当场抓住。**先跑自检，再交付。**

## P20. 四层阶梯的「能力边界」是实测出来的，不是推理出来的 ★ 最重要的一条

**背景**：L1 独立重实现、L3 结构审计看起来都很"硬"，容易让人以为"过了这两层就稳了"。

**实测方法（可复现）**：对一份已验证通过的成品，注入三类**本该被抓到**的陷阱，看每层的反应——
> 一键复现：`python scripts/make_traps.py --out ./边界实验`（**自带 demo 样本，不依赖外部文件**）。
> 完整实验记录、根因分析与两处实现坑见 `references/boundary-experiment.md`。

| 陷阱 | 注入方式 | 公式 | 缓存 |
|---|---|---|---|
| A 缓存篡改 | 把 `<v>` 改成 `12345` | 正确 | 错 |
| B 公式改错 | 引用 `$B$7:$B$16` → `$B$8:$B$16` | 错 | 未同步（仍是旧值） |
| C 越界引用 | 引用 → `$B$7000:$B$7016` | 错 | 未同步 |

**实测结果**：

| 层 | 陷阱A | 陷阱B | 陷阱C |
|---|---|---|---|
| L1 独立重实现 | ✖ 漏报 | ✖ 漏报 | ✖ 漏报 |
| L2 多引擎重算 | ✔ 命中 | ✔ 命中 | ✔ 命中 |
| L3 结构审计 | 仅 `--expect` 命中 1/2 | ✖ 漏报 | ✖ 漏报 |
| L4 不变量 | ✖ 漏报 | ✖ 漏报 | ✖ 漏报 |

**根因**：`L1` 走 `openpyxl(data_only=True)`、`L3` 走静态 XML 分析，**两者读的都是缓存**，
因此共享同一个盲区。L4 检查的是"性质"而非数值，自然也看不出来。

**固化下来的三条纪律**

1. **L2 不是"锦上添花的第二意见"，是唯一能回答"引擎重算是不是这个数"的一层。**
   任何场景下都不允许省略。只跑 L1+L3 就宣布"已验证"，等于自欺。
2. **L4 只能证明"逻辑自洽"，不能证明"数字正确"。** 排名连续、降序、Top-K 一致——
   这些在陷阱场景里**依然全部成立**（错的数字同样满足这些性质）。别把 L4 全绿当成数字对了。
3. **交付话术必须与层数匹配**：走了几层就说几层。"我做了 4 项检查" ≠ "已验证"。

> 附带发现（已修复）：`recalc_verify.py` 在引用越界时，引擎通过 COM 读回的是
> **负 HRESULT 错误码**而非 `#REF!` 字符串——实测 `=#NUM!` 单元格返回 `-2146826252`（`0x800A07F4`，
> 低 16 位 `2036` = `xlErrNum`）。这会让比对列显示成一串无意义的大负数。
> **已加 `normalize_cell_value()`**：凡 `0x800Axxxx` 形态的负数按低 16 位映射回
> `#NULL!/#DIV/0!/#VALUE!/#REF!/#NAME?/#NUM!/#N/A`，正常值与非错误串原样放行。
> 修复后同一实验输出变为 `引擎='#NUM!'`，可读且**不影响检出**（仍报 48 处不一致）。
> **教训**：写错误码映射表时不要凭记忆硬编码 HRESULT——
> 用 `v & 0xFFFF` 取常量再映射，否则差一个偏移就全部失配。
